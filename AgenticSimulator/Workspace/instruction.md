# 任务目标

你是负责源仿真器校准和策略续训的 coding agent。在同一会话中完成两个阶段：

1. 使用初始策略 P0 比较源环境和目标环境，修改源物理实现，使源环境产生的
   行为尽可能接近目标环境。目标环境保持固定。
2. 选定校准候选后，在该固定校准环境中继续训练策略，争取恢复 P0 在初始源环境
   中的表现，并通过目标环境 rollout 检查续训策略的迁移效果。

P0 是宿主中的 `default` 策略。续训沿最新 checkpoint 推进：
P0 → P1 → P2 → …。是否沿用训练配方、是否继续下一轮、何时观察和结束，由你
根据反馈决定；不要求达到预设训练轮数，也不要求每轮修改代码。

物理差异可能来自参数取值、缺失的物理状态或缺失的作用机制。根据实验反馈
判断需要修改什么，使用已有 Isaac Sim / Isaac Lab 接口实现，不修改或重新编译引擎。

校准依据是两侧行为差异是否缩小。任务成功与否只是表现的一部分；即使两侧
都完成任务，也需要检查运动过程是否一致。源侧任务奖励提高本身不能证明校准有效。

# 开始工作

先阅读 `tools.md`，了解实验命令、反馈格式、代码接口和提交方式。
结合 `reference/` 中的只读资料，了解源环境的场景构建、配置加载、policy 的
观测与动作约定，以及物理代码的调用时机。再阅读 `source/` 中的初始物理实现
和 `training/` 中的初始训练配方。
参考配置描述的是基准环境；当前候选会在环境创建前修改物理参数，并可在物理
子步中施加额外作用，因此应结合候选代码和实际反馈判断当前源环境的行为。

查询当前预算：

```bash
python scripts/env.py status
```

在修改前，使用 `--policy-id default` 获取 P0 在初始源环境与目标环境中的 rollout
反馈，保留请求编号和原始记录，作为校准对照及后续恢复表现的基准。校准阶段
始终使用 P0，使用相同的回合编号和种子对照两侧表现。一次双侧请求自动共用
同一个种子；不指定 `--seed` 时，每次请求由宿主随机生成种子，并通过响应顶层
的 `seed` 返回。
分开运行两侧或复查已有条件时，显式指定相同的 `--seed`。每次 rollout 都从
新初始化的环境开始，不延续上次实验的物理状态。

在预算允许的范围内，使用多个种子覆盖任务定义的不同初始条件，不只围绕一个
种子调整源环境。相同种子用于尽量保持采样条件可比，仍需检查实际反馈。

# 观察与推理

利用已公开的源侧状态、轨迹、评价、日志和视频分析源行为；目标侧仅依据宿主
发布的反馈判断。不要尝试读取目标私有配置、内部状态或宿主私有文件。
不要假定未提供的目标信息已经可用。

关注可以在两侧对照的现象，例如运动方向、接触时机、滑动、抓取后的相对运动、
释放后的运动以及任务完成过程。根据实际反馈选择有意义的比较方式，说明
哪些差异来自直接观察，哪些解释仍是假设。

相似的表现可能由不同物理原因产生。将不确定性保留在判断中，用后续实验
区分假设；不要仅凭一个结果就声称恢复了目标的真实参数。

# 校准阶段

按以下过程迭代：

观察两侧表现 → 提出物理假设 → 修改源实现 → 执行候选 → 比较反馈 → 修正判断。

- 每次修改前，说明它针对什么现象、预计会怎样改变源行为。
- 优先进行能够判断效果的修改，避免同时改变大量无关因素。
- 执行后检查实际反馈是否支持预期，比较当前候选与初始版本及已有候选。
- 比较物理改动时复用已有种子；判断改进是否适用于其他条件时，再使用新种子
  获取源、目标对照反馈。不要把不同初始条件造成的差异直接归因于物理修改。
- 修改无效或使差异增大时，修正实现或恢复更有证据支持的版本。
- 根据实时预算安排实验，为最终候选的执行与比较留出次数。

在 `scratch/` 中记录请求编号、候选编号、policy、回合编号、种子、修改原因、
主要观察和未解决的问题。
可以编写本地分析脚本处理已公开的反馈。保留原始证据，并区分原始记录与
自行计算的比较结果。相同 policy、回合编号和种子下可复用已有目标反馈；
需要其他条件的对照或新增证据时，再请求目标实验。

# 续训阶段

当已有证据支持某个校准候选时，从已执行的源实验中选择其 `candidate_id`，
记录选择理由，然后提交首次训练请求：

```bash
python scripts/env.py train --candidate-id <校准候选编号>
```

宿主完成首次训练请求的准备后固定该候选；之后的源 rollout 和训练均使用这个
已归档版本，修改工作区 `source/` 不会改变训练所用的物理候选。目标环境继续固定。

每次训练从最新成功登记的 checkpoint 继续，新增 1000 iterations，每 100
iterations 保存 checkpoint，默认使用 4096 个并行环境。训练代码必须遵守这轮
训练量和保存设置。宿主保存模型并返回策略编号，后续通过编号使用策略。
训练本身不自动执行评价 rollout，也不自动开始下一轮。

根据训练日志、公开配置和已有 rollout 反馈，决定下一步：

- 沿用配方：若认为现有配方仍适合继续学习，保持 `training/` 不变，直接再次
  调用 `python scripts/env.py train`。
- 调整配方：若反馈支持调整奖励、课程或训练代码，先说明依据和预期效果，
  修改 `training/`，再调用 `train`。每轮训练都会保存当时的训练代码版本。
- 观察表现：按需要请求源或目标 rollout。默认 `latest` 使用最新策略；
  `--policy-id default` 使用 P0，也可以指定已登记的策略编号做对照。
- 结束：已有足够依据、预算不足或暂时没有有依据的改进方向时，提交 `finish`。
  可以在 P1 后结束。

续训始终从最新成功登记的策略出发，不回退到较早 checkpoint 分支训练。
失败的训练不会推进策略编号；发生错误时结合返回结果和 `status` 中的
`latest_policy_id`、`training_rounds_completed` 确认当前进度。
训练实际启动一次消耗一次 source 实验预算，安排时为必要的观察留出次数。

自行选择能说明表现是否恢复的比较指标和观察方式，记录判断依据，保持已有
任务成功判定不变。将校准环境中的策略表现与已保存的 P0 初始源环境基准比较，
将固定目标环境中的迁移表现单独记录。训练奖励提高本身不能证明任务表现恢复，
也不能证明迁移有效；不要求固定次数的评测或每轮都执行 rollout。

在 `scratch/` 中持续记录校准候选、训练请求、训练代码候选、父策略和新策略编号、
配方是否修改及原因、观察结果和下一步判断。区分训练完成、表现改善和达到自己
所述恢复标准这三件事。

# 修改范围

源物理代码放在 `source/`，训练配方放在 `training/`，分析脚本、笔记和临时文件
放在 `scratch/`。保留物理和训练入口的函数签名及返回约定，可以在各自目录内
组织必要的辅助模块。训练配方应使用宿主提供的校准环境、checkpoint 和输出目录。

`reference/` 是固定参考资料，修改物理应在 `source/` 中完成。宿主保存候选时
只归档 `source/`，训练代码另行归档 `training/`，不会将 `reference/` 一起复制到
候选运行目录。各自需要的辅助代码放在各自目录内，不依赖工作区的 `reference/`
路径进行导入。

两个阶段都保持观测与动作约定、控制周期、任务目标、最终评价规则、成功判定
和录像设置固定。校准阶段保持 P0 权重和奖励固定；物理改动应体现对动力学或
接触过程的解释，不通过改写观测、回放目标轨迹或加工录像制造一致的反馈。
续训阶段允许调整训练奖励、课程和训练代码，并通过训练更新策略权重；调整应
服务于原任务，不改变固定校准候选的动力学，也不改写成功判定或公开实验记录。

不要修改只读指令、客户端、参考资料或宿主发布的实验记录。一次只提交一个实验请求，
等待返回后再修改源代码或训练代码，不在后台并发修改或提交。

失败也是实验记录。根据错误和已有证据决定如何修正，不自动重发通信中断的请求，
不将超时、崩溃或缺少报告直接认定为基础设施故障，也不丢弃失败来夸大结果。

# 完成与提交

当你认为已有充分证据支持当前结果、预算无法支持进一步实验，或无法继续取得
有依据的改进时，结束会话。正常流程提交固定校准候选和最新策略。

在 `scratch/` 中保留简要总结：校准候选编号、主要物理改动、完成训练轮数、最新
策略编号、配方变化、支持判断的请求编号与观察，以及仍存在的差异和不确定性。
分别说明校准依据、相对于 P0 初始源环境基准的恢复情况和目标环境迁移情况。
没有观察到的效果应标为尚未确认；若只比较了单一种子，说明结论的局限。
当前没有自动校准或恢复达标阈值，不宣称通过了未提供的验收标准。
响应中的 `ok` 仅说明执行状态。

进入续训阶段后，使用以下命令提交固定校准候选和最新策略：

```bash
python scripts/env.py finish
```

提交不会额外训练或执行 rollout，也不会采用尚未运行的代码修改。最终策略为
最新成功登记的策略；此前策略可以用于 rollout 对照，但不作为替代的最终提交。

如果尚未进入续训阶段便必须结束，说明原因，从已执行的源候选中选择有依据的版本：

```bash
python scripts/env.py finish --candidate-id <候选编号>
```

候选编号对应宿主已保存的代码版本。若修改后尚未执行，先运行该版本，再选择
其候选编号。尚未固定校准候选且没有可提交的候选时，使用不带候选编号的 `finish`
结束。成功结束后停止实验，在最终回复中简要报告候选编号、最终策略编号、
主要结论和剩余限制。
