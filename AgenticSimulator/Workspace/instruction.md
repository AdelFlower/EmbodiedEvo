# 任务目标

你的目标是提高策略在固定目标环境中的任务表现。从初始策略 P0（`default`）开始，
比较源、目标环境中的行为，提出对物理差异的解释。每次根据假设修改源物理后，
先用当前策略观察修改效果，再在该版本上从最新 checkpoint（保存的训练状态）续训一轮。
用新策略做 rollout，根据目标侧的公开反馈判断是否达标。未达标时，用这次反馈开始下一轮。

物理差异可能来自参数取值、缺失的物理状态或缺失的作用机制。使用已有的
Isaac Sim / Isaac Lab 接口实现源物理改动。

# 开始工作

先阅读 `tools.md`，了解实验命令、反馈格式、代码接口和提交方式。
结合 `reference/` 中的只读资料，了解源环境的场景构建、配置加载、policy 的
观测与动作约定，以及物理代码的调用时机。再阅读 `source/` 中的初始物理实现
和 `training/` 中的初始训练配方。
参考配置描述的是基准环境；当前候选会在环境创建前修改物理参数，并可在物理
子步中施加额外作用，因此应结合候选代码和实际反馈判断当前源环境的行为。

使用 `python scripts/env.py status` 查询预算。修改前先用 P0 做基准 rollout。
你可以按需要在源环境、目标环境或两侧探测。要直接比较两侧，可用一次双侧请求：

```bash
python scripts/env.py rollout --environments source target --policy-id default
```

保留请求编号、种子和原始记录。一次双侧请求共用种子，分开请求时可用相同的
`--episode-id` 和 `--seed` 对照。每次 rollout 都从新初始化的环境开始。
在预算允许时，用多个种子观察差异是否也出现在其他初始条件下。

# 观察与推理

利用已公开的源侧状态、轨迹、评价、日志和视频分析源行为；目标侧仅依据宿主
发布的反馈判断。不要尝试读取目标私有配置、内部状态或宿主私有文件。
不要假定未提供的目标信息已经可用。

根据两侧公开的反馈，自行选择可以对照的现象。用同一策略比较修改前后的源侧表现
与目标侧表现，记录差异如何变化，并区分直接观察到的结果和对原因的推测。

相似的表现可能由不同物理原因产生。将不确定性保留在判断中，用后续实验
区分假设；不要仅凭一个结果就声称恢复了目标的真实参数。

# 一轮改参与续训

1. **提出假设并修改。** 根据当前策略在源、目标环境中的行为，说明观察到的差异、
   怀疑的物理原因和预期效果，再修改 `source/`。相同策略、回合编号和种子下，
   可以复用已有的目标反馈。
2. **用当前策略观察这次改动。** 调用 `python scripts/env.py rollout --environments source`。
   默认的 `latest` 在第一轮指 P0，之后指最近成功登记的策略。记录实际表现是否符合假设，
   从响应的 `results.source.candidate_id` 取出这次运行的源物理版本编号。
3. **在刚观察的版本上显式续训一次。** 例如，上一步返回 `c000002` 时，运行
   `python scripts/env.py train --candidate-id c000002`。每轮从最新 checkpoint
   新增 1000 次迭代，每 100 次保存一次，默认使用 4096 个并行环境。可以沿用 `training/`
   中的配方，也可在反馈支持时调整训练奖励、课程或训练代码，记录改动依据。
4. **评估新策略并决定下一步。** 用新策略做 rollout，重点观察固定目标环境里的任务表现。
   可用 `python scripts/env.py rollout --environments target` 观察最新策略，
   也可按需要在当前源环境或两侧做对照。根据目标侧证据自行判断是否达标。达标则提交
   `finish`，否则根据本轮反馈提出下一次物理修改，从刚登记的策略继续。

例如，第一轮在候选 A 上从 P0 训出 P1。下一轮用 P1 观察修改后的 B，取得 B 的编号，
再在 B 上从 P1 训出 P2。单独做探测时可连续调用 rollout。每次物理修改对应一轮显式训练。

在 `scratch/` 中记录每轮假设、候选编号、父策略和新策略编号、训练配方版本、请求编号、
种子和判断依据。结合训练日志与源侧轨迹解释现象，依据实际公开的目标侧反馈判断任务表现。
每轮开始前，为改参后的源侧观察、一次源侧训练和训练后的评估预留实验预算。
若请求失败，保留记录，通过 `status` 中的 `latest_policy_id`、`latest_policy_candidate`
和 `training_rounds_completed` 核对实际进度。

# 修改范围

源物理代码放在 `source/`，训练配方放在 `training/`，分析脚本、笔记和临时文件
放在 `scratch/`。保留物理和训练入口的函数签名及返回约定，可以在各自目录内
组织必要的辅助模块。训练配方应使用宿主提供的校准环境、checkpoint 和输出目录。

`reference/` 是固定参考资料，修改物理应在 `source/` 中完成。宿主保存候选时
只归档 `source/`，训练代码另行归档 `training/`，不会将 `reference/` 一起复制到
候选运行目录。各自需要的辅助代码放在各自目录内，不依赖工作区的 `reference/`
路径进行导入。

各轮共用相同的观测与动作约定、控制周期、任务目标、成功判定、评价规则和录像设置。
用同一策略和相同奖励观察源物理改动的效果，保留原始轨迹和录像。
策略权重通过训练更新。训练配方使用本轮候选提供的动力学，奖励和课程的调整服务于原任务。

不要修改只读指令、客户端、参考资料或宿主发布的实验记录。一次只提交一个实验请求，
等待返回后再修改源代码或训练代码，不在后台并发修改或提交。

失败也是实验记录。根据错误和已有证据决定如何修正，不自动重发通信中断的请求，
不将超时、崩溃或缺少报告直接认定为基础设施故障，也不丢弃失败来夸大结果。

# 完成与提交

根据固定目标环境的公开反馈判断最新策略是否达到任务目标。达标时提交 `finish`。
预算耗尽或实验无法继续时也可结束，说明实际进度和未能确认的效果。
在 `scratch/` 中总结最新策略、对应的源候选、完成轮数、主要修改以及支持判断的
目标侧请求编号和观察。注明有限种子或缺失反馈带来的局限。响应中的 `ok` 表示请求执行状态。

```bash
python scripts/env.py finish
```

已有续训策略时，此命令提交最近成功登记的策略及训练出它的候选。后续探测得到的
其他候选只记录在对应的 rollout 中。若首轮策略尚未成功登记就必须结束，
可显式传入已归档候选编号与 P0 一起提交，或直接 `finish` 结束并留空最终候选和策略。
提交后在最终回复中报告候选编号、策略编号、主要结论和剩余限制。
